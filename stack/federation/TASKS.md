# stack/federation — TASKS (WBS 3.3, 4.1)

Goal: two independently owned islands authenticate each other's subscribers over an overlay without sharing keys, and behave correctly when the link between them dies. Design authority: [RFC-0003](../../rfcs/rfc-0003-roaming.md) (roaming), [RFC-0005](../../rfcs/rfc-0005-island-identity.md) (allocations, overlay identity). Milestone **M3** = 3.3-c passing in the lab.

`[SIM]` throughout — both islands run as software on one host (or two hosts if available; the tasks say which parts change). Nothing radiates.

Prerequisites: island-init 2.1-a..g (allocations and rendering exist), sim-tools 3.2-e (rig-safe subscriber provisioning).

---

## 3.3-a — Two islands on one host

**Problem to solve first:** every island today renders the same *node-internal* addressing (`core_net` 10.10.0.0/24, NF addresses 10.10.0.x, `services_net` 10.46.0.0/24, ZMQ ports). Docker refuses overlapping subnets across bridge networks, so a second island cannot start beside the first until node-internal addressing is a per-island render parameter.

**Steps**
1. Add a node-internal addressing block to `island.yaml` (e.g. `node.internal_base: 10.10.0.0/16` from which `core_net`, NF addresses, and any other node-only subnet derive) and template every hardcoded node-internal address in `island_init/templates/` from it — including compose network definitions and healthcheck addresses. `--lab` must still render byte-identically (golden rule: the lab value is today's addressing).
2. Add an `island-B` lab allocation fixture: same test PLMN `001/01` (RFC-0003 D1's same-PLMN model), **distinct IMSI block** (e.g. `00102…`), distinct UE prefix (`10.47.0.0/16`), services prefix (`10.48.0.0/24`), realm (`islandb.localdomain` or per RFC-0005 naming), DNS zone (`islandb`), node-internal base (`10.20.0.0/16`), distinct compose project names (`COMPOSE_PROJECT_NAME` suffix `-b`).
3. `island.sh` gains `--island <dir>` (or an env var) so two rendered trees (two checkouts or two `island-init` output roots) can be brought up side by side.

**Acceptance**
- Island A (lab) and island B both up on one host simultaneously; each passes its own `stack/core/verify.sh` (a UERANSIM UE per island attaches to *its* island and pings *its* services subnet). Island A's verify output is unchanged from before this task.
- `render --lab` golden-rule test still passes; pytest extended for the addressing derivation.

## 3.3-b — Overlay between islands with allow-lists

**Steps**
1. A `wg-overlay` container per island (upstream WireGuard image, pinned) with keys from `secrets/` (host-side, via the same mount discipline as 2.1-f — the private key stays host-side; the container gets what WireGuard needs and nothing else <!-- VERIFY: cleanest way to give a container a WireGuard interface without exposing the key file more widely than necessary -->), addressing from `island.yaml` (`island.overlay`), peers rendered from a new `federation.peers[]` allow-list (RFC-0003 D2) carrying each peer's overlay pubkey, endpoint, and the prefixes it announces (its node-internal base + services prefix).
2. Routing so that island A's core can reach island B's NF addresses over the overlay and vice versa, **only for allow-listed peers**.

**Acceptance**
- With B allow-listed on A and A on B: from A's AMF container, the SBI port of B's NRF/UDM answers over the overlay; removing B from A's allow-list and re-rendering makes that path fail (and the reverse).
- Killing the overlay container on either side leaves every local island service working (re-run each island's services verify with the overlay down).

## 3.3-c — Home-routed 5G authentication (milestone M3)

**Steps**
1. On island B, register island A's UDM/AUSF in B's NRF with a **SUPI range** covering A's IMSI block (RFC-0003 D1) <!-- VERIFY: Open5GS NRF NF-profile `supiRanges` support and AMF discovery honouring it for AUSF/UDM selection; whether A's NFs must register themselves into B's NRF over the overlay or B can carry static profiles --> and vice versa; rendered from `federation.peers[]` by `island-init`.
2. Provision a subscriber in island A's IMSI block with `resccom-sim` on A only.
3. Attach that subscriber via **island B's** UERANSIM gNB.

**Acceptance**
- The UE registers on B; B's AMF log shows the AUSF/UDM used are A's (over the overlay); A's UDM/AUSF logs show the authentication; the UE's PDU session and breakout ping are served by **B's** SMF/UPF and services subnet (RFC-0003 D1: sessions local). Nothing about the subscriber exists in B's MongoDB (confirmed by query).
- A's home log records the roaming event (which peer, when) — the RFC-0003 D5 disclosure made real.
- If the upstream mechanism does not work as the VERIFY markers hope, a written negative finding with the exact failure is a valid result; RFC-0003's consequences section names SEPP/N32 as the alternative — do not implement it without a Fable design pass.

**VERIFY markers settled — negative finding (2026-09-15).** `stack/federation/two-island.sh roam` + `roam_test.py` is the reproducible vehicle (run `./two-island.sh roam`); it registers A's real AUSF/UDM into B's NRF via `Nnrf_NFManagement` PUT with `ausfInfo`/`udmInfo.supiRanges` covering A's `imsi_block`, provisions a roaming-test subscriber on A only, attaches it via B's own gNB, and prints every acceptance bullet's PASS/FAIL plus B's full AMF log for the attempt. Three independent, compounding failures, each confirmed live against the pinned `gradiant/open5gs:2.8.0`:

1. **`supiRanges` does not survive NRF's own storage.** The OpenAPI-generated `NFProfile`/`AusfInfo`/`UdmInfo` C structs declare a `supi_ranges` field (spec-compliant, `lib/sbi/openapi/model/ausf_info.h`/`udm_info.h`), but: (a) none of `ausf.yaml`/`udm.yaml`/`nrf.yaml`'s shipped samples expose any config knob to populate it — Open5GS's own AUSF/UDM never self-register with one; (b) the compiled `nrfd`/`amfd`/`udmd`/`ausfd` binaries contain zero occurrences of the string `supiRanges` (checked both camelCase and `supi_range`, case-insensitive) — the (de)serialize code for that field is unreachable/dead in this build; (c) **live**: `curl -X PUT .../nnrf-nfm/v1/nf-instances/<id>` with a body carrying `ausfInfo.supiRanges` returns 200 and echoes the request back, but an immediate `GET` on the same instance shows no `ausfInfo` key at all — NRF silently drops it on persist. `roam_test.py`'s registration step reproduces this exact round-trip every run and prints "NEGATIVE FINDING" when it happens (it did, both AUSF and UDM, every run).
2. **A "static profile" doesn't survive NRF's own liveness model either.** A one-shot PUT registers an NFProfile with a declared `heartBeatTimer` (10s here) but nothing to actually heartbeat it. Live AMF log: `[a0000000-...] (NRF-notify) NF registered` at T+0, then `[a0000000-...] (NRF-notify) NF_DEREGISTERED event [type:AUSF]` at T+11s — NRF's own timeout removed it before the UE attach attempt (T+12s) ran. Answers VERIFY marker 2 directly: a genuinely *static* profile is not viable against this NRF; only an actively self-registering, continuously heartbeating NF instance persists — and Open5GS's own AUSF/UDM config (`sbi.client.nrf`) only ever points at *one* NRF, so A's real AUSF/UDM processes cannot themselves heartbeat into both A's and B's NRF simultaneously without running dedicated second processes per federation peer (operationally unworkable for N peers, and a config/orchestration problem this repo cannot solve by templating alone).
3. **Even setting aside (1) and (2), AMF did not re-select per subscriber.** With the fake AUSF profile already expired, AMF's `gmm-sm.c`/`nas-path.c` fell straight back to the one AUSF instance it already held from its own initial NRF discovery (B's own, `10.20.0.11`) and called it directly for the roaming SUCI — no fresh NRF discovery keyed on SUPI/SUCI was observed. B's own AUSF answered "Cannot find SUCI [404]" (it has never heard of this subscriber, correctly), and AMF issued `Registration reject [7]` (5GS services not allowed). B's Mongo has zero documents for the roaming IMSI throughout (confirmed by query) — the one acceptance bullet that *did* hold, for the uninteresting reason that authentication never got far enough to write anything anywhere.

**Conclusion:** Open5GS 2.8.0 cannot select among multiple same-PLMN AUSF/UDM instances by subscriber identity — SUPI-range NF discovery, as TASKS.md step 1 describes it, does not work against this pinned version, for reasons upstream would have to fix (CLAUDE.md "never fork upstreams" forecloses patching it here). RFC-0003 open question 1 is answered accordingly. RFC-0003's own fallback — SEPP/N32 under a distinct-PLMN model — needs a design pass this task does not do (explicitly out of scope here); it also doesn't apply as-is, since both lab islands deliberately share PLMN `001/01` (RFC-0003 D1's same-PLMN model), and SEPP/N32 roaming is 3GPP's distinct-PLMN mechanism. 3.3-c's acceptance is therefore not met and is not expected to be met without either an upstream fix or a SEPP/N32 design pass; `./two-island.sh roam` stays in the tree as the reproducible check for whenever either changes. 3.3-d (home-routed 4G) rests on the same NRF-adjacent (Diameter realm routing) family of upstream mechanics and should be re-scoped with this finding in mind before starting it.

## 3.3-d — Home-routed 4G authentication

**Known blocker found in 3.3-a (2026-09-14):** per-island Diameter realms cannot be rendered yet — `gradiant/open5gs` ships one fixed self-signed freeDiameter cert per NF with `localdomain` hostnames, and HSS/MME abort at startup on the cert hostname check for any other realm. That is why `island.example.b.yaml` keeps `realm: localdomain`. Realm routing needs distinct realms, so step 0 is: `island-init` generates per-island freeDiameter certificates (CA + per-NF certs matching `<nf>.<island realm>`) into `secrets/` at `new` time and the templates point `TLS_Cred`/`TLS_CA` at mounted copies — a configuration change, not an upstream fork (the `.conf` paths are upstream's own knobs). Do this before the realm-routing step.

**Steps**
1. freeDiameter realm routing on B's MME toward A's HSS for A's realm (rendered from the allow-list) <!-- VERIFY: freeDiameter routing extension/config for realm-based forwarding to a remote peer; whether MME derives the realm from the IMSI (3GPP `epc.mnc…3gppnetwork.org` style) or per-island realms must be mapped explicitly -->.
2. Attach an A-subscriber via B's srsRAN 4G ZMQ rig.

**Acceptance**
- Same shape as 3.3-c on the EPC path: auth by A's HSS, session by B's SGW/SMF/UPF, nothing about the subscriber in B's Mongo.

## 4.1 — Partition drills (the two-island exercise)

**Re-scoped and corrected 2026-09-17, before execution.** The original steps (kept at the end of this section) predate the M3 design (3.3-c v2–v2h); two premises no longer hold, verified from source in review, and the Matrix half is out of scope.

- *"Bounded vector caching, then honest failure after exhaustion"* (RFC-0003 D3) is an EPC-era framing. In the M3 setup B holds **no key** for the roamer — a policy-only inbound-roamer record (3.3-c v2h) — and authentication is home-routed to A over SEPP. Open5GS's AMF has no vector cache to size: whether it re-contacts home is gated on `SECURITY_CONTEXT_IS_VALID(amf_ue)` (`src/amf/gmm-sm.c:1752`, v2.8.0) — an integrity-protected request under a valid context is a local registration *update*; anything else goes to `nausf-auth` (home). So the drill **measures** the real behaviour; it does not build a cache. The `<!-- VERIFY -->` on vector batch sizing is withdrawn.
- The drill needs both islands **up** across the partition sequence; `cmd_roam` tears down on its `trap cmd_down EXIT`. A dedicated `drill` command holds them up and tears down only at the end, with 3.3-b follow-up 8's guarantee intact (island A's pre-existing core is never `down -v`'d).
- **Matrix federation (RFC-0003 D4) is out of scope here and deliberately not enabled.** `stack/services/config/matrix-synapse/homeserver.yaml` has no federation listener, `federation_domain_whitelist: []`, `trusted_key_servers: []`; and the overlay forward filter passes only SEPP N32 ports, so a cross-island room cannot run. Proposed as its own task **4.1-b — Matrix federation across the overlay**: enable Synapse's federation listener; whitelist exactly the peer island's realm (RFC-0005) in `federation_domain_whitelist` (never open federation); carry 8448 over the overlay the way SEPP N32 is carried today (route injection + `allowed-ips`); widen `wg-overlay`'s forward filter to that one port from the peer's Synapse address only; then a threat-model **M8 pass** (a hostile peer now reaches Synapse, not just SEPP — room-state exposure, whether server ACLs suffice); and only then the original step 3's measurement (drop the overlay past Synapse's federation retry window, restore, confirm queued delivery, record the tolerance). Not started.

**The drill (`two-island.sh drill --ue oai`).** `cmd_up` + the `roam --ue oai` attach flow (refactored into shared functions `roam_prepare`/`oai_gnb_up`/`oai_nrue_config`/`oai_nrue_up`/`breakout_ping`, so `roam` is unchanged and the drill reuses it verbatim), then, with both islands held up, five steps each printing evidence and an `AS EXPECTED`/`DIFFERENT FROM EXPECTED` verdict:
- **(a)** roamer attached, served by Local Breakout on B (the M3 state); breakout ping 0% loss; A's SEPP forwarding lines quoted.
- **(b)** stop B's `wg-overlay` (the link `verify.sh` tests); confirm the established PDU session keeps passing user-plane traffic (B's own UPF anchors it).
- **(c)** with the overlay down, detach/re-attach the roamer nrUE (a fresh registration); record B's AMF's own failure — auth cannot reach A's AUSF over SEPP.
- **(d)** with the overlay down, `resccom-sim sub add` a **local B subscriber** (IMSI `999700000000001`, B's own block, full credentials in B's own store — not the roamer's home IMSI, not an inbound-roamer record) and show it registering and breaking out locally.
- **(e)** start `wg-overlay` again; time recovery; re-attach the original roamer; print A's SEPP log for the whole drill (RFC-0003 D5).

**A defect found and fixed during execution (run 1 → run 3).** The first cut dropped the overlay with `docker network disconnect` of B's `wg-overlay` from `wan_net` and read the link down from a single N32-c (7778) probe. That produced a real, misleading result: the probe read "down" while the **N32-f** port (7779, the one home-routed authentication actually forwards over) was still carrying a genuine `201` authentication response home — an asymmetric, half-open partition. Step (c) therefore did not test a partition (3/5 steps `DIFFERENT FROM EXPECTED`, recorded, not hidden). The drill now **stops the `wg-overlay` container** (which runs no WireGuard and cannot carry either port) and `overlay_probe` gates on **both** N32 ports before any step calls the link down. `docker network disconnect`'s asymmetric behaviour on this host is not root-caused further; stopping the container makes the partition deterministic, and the task's own text sanctioned either method.

**Acceptance**
- The drill runs end-to-end with every step's evidence printed (ping results, the re-registration failure, the guest attach, the recovery), island A's core untouched, tree clean at hand-off. — MET
- Numbers recorded as measured in `docs/poc-writeup.md` (whether the live session survived, recovery time). — MET
- `playbook/drills.md` describes the drill in operator terms, referencing the script. — MET
- STATUS.md 4.1 updated; RFC-0003 D3 corrected. — MET

**Result — done, live-verified twice (2026-09-17), 5/5 steps AS EXPECTED both runs.** `./two-island.sh --log-level debug drill --ue oai`, run twice, identical shape both times:

## 3.3-b follow-up — reproducible two-island harness, and overlay coverage in the unplug test (do before 3.3-c)

Found in review (2026-09-14). 3.3-b's acceptance was run live and passed, but:

1. **The cross-peering procedure is not scripted.** Reproducing the acceptance means hand-generating B's keys, editing both islands' `federation.peers[]`, rendering both trees, and bringing four compose projects up in the right order — none of which a reviewer, a partner lab, or the 4.1 drill can do from the docs in one command. Ship `stack/federation/two-island.sh up|down|verify`: creates the second checkout (or takes `--b-dir`), generates B's identity from `island.example.b.yaml`, cross-populates `federation.peers[]` in *transient copies* of both island files (never the committed fixtures), renders, brings up both islands' `stack/core` + `stack/federation`, runs `verify.sh` both ways, and tears everything down. This becomes the acceptance vehicle for 3.3-c/d and 4.1.
2. **The unplug test cannot see the overlay.** `wg-overlay` joins `services_net` with a dynamic address (`- services_net`), and a peered `amf` joins it as `services_net: {}` — both are WAN-capable memberships the `WAN_TOUCHING_IPS` guard (which only parses fixed `ipv4_address:` entries) will never flag. In a peered island the unplug test would under-cover exactly the two containers that talk to the outside. Fix: give `wg-overlay` and the peered `amf` fixed `services_net` addresses rendered from the services prefix (consistent with every other container), **and** make the guard fail loudly on any dynamic membership of a non-internal network so this class cannot recur.
3. **Record in the threat model (M8):** the overlay's masquerade makes a peer's traffic appear as a local `core_net` source, so an allow-listed island can reach *every* NF, not only NRF/AUSF/UDM/HSS. The allow-list gates *which islands*, not *which services*. 3.3-c must add a forward-filter in `wg-overlay` restricting tunnel-origin traffic to the authentication NFs' addresses/ports once that set is known; until then, this is a documented gap, not a mitigation.

**Acceptance**
- `two-island.sh verify` passes on a clean host in one command and is what STATUS cites for 3.3-b/c.
- With a peer configured, `unplug-test.sh`'s guard lists `wg-overlay` and `amf`'s services addresses (or fails loudly if it cannot); with no peer, the lab profile is unchanged (golden rule).
- `docs/threat-model.md` M8 row updated with the NF-reach gap and the 3.3-c forward-filter as its required mitigation.
4. **Identity drift is undetected.** After the live test, `secrets/lab/wireguard.key`'s public half no longer matched `island.yaml`'s declared `wireguard_public_key` (regenerated keys, fixture restored, nothing re-synced) — peers built from `island.yaml` would never handshake, and nothing would say why. `island-init check` must derive the public key from the mounted/host key file when it is present and fail on mismatch; `wg-up.sh` must assert the same at startup and exit loudly.
5. **Schema evolution broke existing instances silently.** 3.3-b made `federation.peers` required; the already-generated instance `island.yaml` (pre-3.3-b) then failed `check` while `island.sh up` happily kept running on its stale render. Rule: a schema change that adds a required field ships an `island-init migrate` step (default values, re-sign under the operator's key) and `island.sh up` runs `check` on the instance before bringing anything up.
6. **`stack/federation/verify.sh` exits 1 silently when no peers are configured.** Say so and exit 0 ("no peers in island.yaml — nothing to verify"); reserve non-zero for real failures.

**Additional acceptance**
- `island-init check` fails with a clear message when the key file's public key differs from the declared one; `wg-up.sh` refuses to start on the same condition.
- A pre-3.3-b instance file passes `check` after `island-init migrate`; `island.sh up` refuses an instance that fails `check`.
- `stack/federation/verify.sh` on an unpeered island prints the no-peers message and exits 0.
7. **`two-island.sh` leaves island A peered and destroys island A's data (found in review, 2026-09-15).** After `verify` (exit 0, all checks passed both directions) the checkout is dirty: `stack/core/compose.yaml` still carries the peered `amf` block and `stack/federation/config/wg-up.sh` still lists B as a peer — the *identity* copies were transient, the *rendered outputs* were not — so a following `stack/federation/verify.sh` "no-peer" run tried to reach island B, and the golden-rule test would fail on the next `pytest`. `down` also runs `down -v` on island A's core, wiping the subscriber volume of whatever island the lab was running. Fix: (a) at the end of `verify` and in `down`, re-render island A from its own unpeered `island-init/island.yaml` (`island-init render --file … --repo-root .`) and assert `git status --porcelain -- stack/` is empty, failing loudly otherwise; (b) never `down -v` island A unless the harness started it — track that in a state file — and document that `verify` restarts A's UE rig; (c) add the post-run clean-tree assertion to the harness's own acceptance.

**Additional acceptance (item 7)**
- Immediately after `two-island.sh verify` on a clean tree: `git status --porcelain` is empty, `stack/federation/verify.sh` reports "no peers" and exits 0, and island A's mongo volume still holds the subscribers it had before the run.
8. **Item 7's state file was trusted from disk, so an interrupted run could still destroy island A's core (found live, 2026-09-17).** `up` wrote `.two-island-a-preexisting` only when the file was absent ("a repeat `up` leaves an existing answer alone"); a `roam` run that died before `down`'s `rm -f` left a stale `a_core_preexisting=0` behind, the next run's `up` trusted it, and its `down` ran `down -v` on island A's real dev core — 16 containers and the mongo volume gone, one orphan `sepp` left (recovered via `island.sh up`, since subscribers live in the sim-tools store). Fix (done 2026-09-17): `up` re-detects island A's live state first thing, every time, overwriting the file (`record_a_core_preexisting`); "from nothing" now means no container *and* no volume of A's compose project (an `island.sh down` keeps mongo's volume); `down` destroys A's core only on an explicit `=0`, and treats a missing file as ambiguity that leaves A up. Principle: leak, never destroy. Accepted cost: a retried `up` after this run's own failed one now leaves A's core up.

**Additional acceptance (item 8)**
- With island A's core up and a planted stale `.two-island-a-preexisting` reading `a_core_preexisting=0`: `two-island.sh verify` rewrites it to `=1` before touching A, passes, and leaves A's core (all 16 containers) and `core_mongo-data` in place; a standalone `two-island.sh down` with no state file at all also leaves A's core up. Verified live 2026-09-17.

## 3.3-c v2 — Home-routed 5G authentication via SEPP/N32, distinct PLMN per island (milestone M3, re-scoped 2026-09-15)

Supersedes 3.3-c's mechanism after its negative finding (kept above, reproducible with `two-island.sh roam`). Design authority: RFC-0003 D1 amendment, RFC-0005 D2 (amended). Upstream reference: Open5GS v2.8.0 ships `src/sepp` and three-PLMN roaming example configs (`configs/examples/5gc-sepp1-999-70.yaml.in`, `5gc-sepp2-001-01.yaml.in`, `5gc-sepp3-315-010.yaml.in`, plus `5gc-no-scp-sepp*` variants) — read them first; the task is to render that topology from `island.yaml`, not to invent one. <!-- VERIFY against those files: which NF configs carry the roaming knobs (AMF/NRF/SCP/SEPP), whether the no-SCP variant suffices for this stack (we run no SCP), N32-c/N32-f ports and TLS expectations, and how the visited AMF derives the home PLMN from the SUCI -->

**Steps**
1. `island.yaml` schema: `allocations.plmn` becomes per-island; `federation.peers[]` entries gain the peer's PLMN and its SEPP N32 endpoint (over the overlay). Lab fixtures: island A stays `001/01`; island B becomes `999/70` (mirroring upstream's example pairing) with an IMSI block under it; golden rule still holds for A.
2. Render a `sepp` service into `stack/core/compose.yaml` (unmodified `gradiant/open5gs` image, `open5gs-seppd`, pinned) and its config from upstream's example, plus the AMF/NRF (and SCP, only if the no-SCP variant proves insufficient) roaming settings, all from `island.yaml`/peers — rendered only when a peer exists (unpeered islands byte-identical).
3. Narrow `wg-overlay`'s forward filter (3.3-b follow-up 3) to the peer SEPP's N32 port(s); NRF/AUSF/UDM are no longer reachable from the tunnel.

The re-run showed the v2c stall does not reproduce and that the real block is one hop later: **A's AUSF profile carries no FQDN, so B's AMF cannot take the SEPP path** — `ogs_sbi_send_request_to_client()` (`lib/sbi/path.c:805`) routes via SEPP only when the target client has an FQDN whose PLMN is foreign (`ogs_sbi_fqdn_in_vplmn`, `lib/sbi/context.c:3107`); otherwise it dials the target directly, which across islands is exactly what the overlay forward filter forbids.

That is why upstream **addresses every NF on the inter-PLMN path by its 3GPP FQDN, as the NF's *primary* listener** — `nrf: sbi: server: - address: nrf.5gc.mnc001.mcc001.3gppnetwork.org` (the `127.0.2.10 / port: 7777` lines are commented out), `ausf: sbi: server: - address: ausf.5gc.mnc001.mcc001.3gppnetwork.org`, likewise SMF/UDM/NSSF, and every NF's `client: nrf: uri: http://nrf.5gc.mnc001.mcc001.3gppnetwork.org` (no port → 80). An NF whose listener is an FQDN advertises that FQDN in its NRF profile (`lib/sbi/context.c:1899–1918`), the visited NF sees a foreign FQDN and sends to its own SEPP with `3gpp-Sbi-Target-apiRoot`, and the home SEPP resolves the FQDN to the real NF. Our IP:7777 addressing can never be routed via SEPP, whatever else is fixed. Before anything else, render what upstream renders.

Two source facts the executor needs, both v2.8.0:

- `ogs_sbi_fqdn_in_vplmn()` and `ogs_sbi_plmn_id_in_vplmn()` return **false whenever the NF has no `serving:` PLMN configured** (`lib/sbi/context.c:3050`, `:3114`); `serving` is parsed per NF from `<nf>.serving` (`lib/app/ogs-config.c:514`). Today only `nrf.yaml` renders it. The AMF (`src/amf/sbi-path.c:110–125`) and SMF (`src/smf/sbi-path.c`) are the NFs that call these checks, so both need `serving` for the FQDN test to ever say "foreign". Both counters were still growing (checked twice, minutes apart, during A's `verify.sh` blocking on its one-shot `/dev/tcp` SEPP probe) without B's `received` ever moving off `0 B`, while A's own `sent` kept climbing — i.e. A is genuinely retransmitting real traffic (WireGuard keepalives and/or the SEPP TCP SYN itself) that never arrives at B, not a one-off dropped packet. The asymmetry in each side's recorded peer *endpoint* is the likely mechanism: B correctly resolves A via the Docker Desktop host gateway (`192.168.65.254:51820`, A's overlay port published to the host), but A's own peer entry for B has drifted to `10.46.0.1:52216` — a `services_net`-local address (A's own bridge gateway, not a route to B at all) on an ephemeral port that doesn't match B's declared `WG_LISTEN_PORT` (51821). WireGuard's own endpoint-roaming behavior (a peer's runtime endpoint is overwritten by the source address of the last authenticated packet received from it, by design, for mobile/NAT-traversal use) is the standard explanation for a peer's endpoint changing after the initial static one from `wg-up.sh.j2`'s rendered `wg set wg0 peer … endpoint …` — but here it appears to have been overwritten with a *bogus*, NAT-hairpinned address, because both wg-overlay containers live on the *same* Docker Desktop host and only reach each other through each other's host-published ports: a reply from B, hairpinned back through the host into A's own bridge network, can arrive looking like it came from A's own gateway rather than from B, and A's kernel then "helpfully" starts sending everything meant for B to that address instead. ## 3.3-c v2h — Inbound-roamer policy records: the last step to M3 (milestone M3, sim path)

**Design (RFC-0003 D1 amendment, write it into the RFC in this task)**
- A federation peer receives, per roaming-enabled subscriber, `{imsi, slice[] with session[] policy}` — nothing else. Any record carrying a `security` key (or `k`/`opc` anywhere) is refused on import: **K never leaves home** stays a hard rule enforced in code, not prose.
- Inbound-roamer records at the visited island are marked (`resccom_inbound_roamer: true`, `home_plmn: {mcc,mnc}`) so local tooling can tell them from the island's own subscribers.
- Transport is out of scope here (a file handed over by the operator; the harness copies it). Signing and exchange over the overlay belong with 3.4 (PKI) — note it there.
- Privacy: the visited island learns which IMSIs may roam to it before they attach. Record this in RFC-0003 D5 and `docs/threat-model.md` M7/M8 as an accepted disclosure with the mitigation "export only subscribers the association marks as roaming-enabled".
